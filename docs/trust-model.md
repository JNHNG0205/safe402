# Safe402 trust model — Phase 3 (LOCAL evaluation)

This describes exactly what a Safe402 audit report proves in this phase, where `confidentialExecutionMode` is `LOCAL` for every audit. It is written to be read alongside a report, not instead of one. Nothing here claims more than the code in `runner/harness/run.ts`, `runner/collectors/strace.ts`, `src/domain/decide.ts`, and `src/reports/*` actually does.

## What is trusted

These are not verified by the audit itself; they are assumptions the whole pipeline rests on.

- **Docker Desktop's kernel isolation.** The runner relies on Docker's namespace, cgroup, and capability isolation (`--network none`, `--read-only` root filesystem, `--cap-drop ALL` with a minimal explicit re-add, `--security-opt no-new-privileges`, `--pids-limit`, memory and memory-swap limits) to actually contain the traced process. Safe402 does not independently verify the container runtime; it trusts Docker Desktop and the host kernel to enforce what it asks for.
- **`strace` running as root inside the container.** The traced tool process runs as an unprivileged user (`nobody`), but `strace` itself is invoked as the container's root user so it can attach to and trace that process; `--cap-add SETUID --cap-add SETGID` (alongside `SYS_PTRACE`) are added specifically so `strace -u nobody` can drop privileges for the traced child. The trust here is that root-run `strace`, not the tool, is producing the trace — Safe402 does not verify `strace`'s own correctness or resistance to ptrace-evasion techniques.
- **The Safe402 operator holding policies and the issuer key.** The research policy (`config/policies/research-agent.yaml`) and the ed25519 issuer signing key (`SAFE402_ISSUER_PRIVATE_KEY`) are controlled by whoever runs the worker. A verifier trusts that this operator has not tampered with the policy definition or the key material outside of what the report itself proves.
- **The trusted helper container used to extract the trace.** After the tool container exits or is killed, a second container — the same operator-controlled runner image, running with full default Docker privileges, not the audited tool's environment — mounts the observation volume read-only and copies its contents to the host. Nothing tool-supplied ever executes in this container; the trust here is that the operator's own image and Docker invocation for this step have not been tampered with, the same trust already placed in the rest of the pipeline.

## What is verified

These are checks the pipeline actually performs and that a report consumer can re-derive independently.

- **Artifact hash at prepare time *and again at run time*.** `resolveArtifact` walks the fixture directory (excluding `node_modules` and `.git`, rejecting symlinks), hashes every file's normalized path and content plus the capability manifest, entrypoint, and lockfile digest, and binds the result under the `safe402/artifact/v1` domain tag. The exact same walk (`copyHashedFiles` in `runner/harness/run.ts`) copies files into the container — and the copy is then **re-resolved** before anything starts: unless it reproduces the audited `artifactHash` (the canonical struct is root-independent), the run throws `ArtifactError('artifact hash mismatch at run time')` and no container is created. `worker/pipeline.ts` re-resolves the stored source directory before the static scan for the same reason, so a directory mutated between resolution and execution ends the job `FAILED` with no capsule rather than producing a decision about content that never ran. Covered by `runner integration > refuses to run a directory whose content no longer hashes to the audited artifact` and `pipeline > an artifact mutated after resolution never reaches ALLOW`.
- **File targets are resolved, never guessed, and an unresolvable one is not silence.** `parseStrace` unescapes every quoted syscall argument (octal, hex, and C escapes) before comparison, tracks each pid's working directory through `chdir`/`fchdir` from the container's initial `/`, inherits it across `clone`/`fork` (sharing it when `CLONE_FS` is set, as the kernel does), and keeps an fd→path map so `openat(dirfd, "name")` resolves too. Only a plain absolute `AT_FDCWD` read-only open outside `/home/tool` may be dismissed as baseline noise; every other open is either evidence with a resolved absolute target or carries the fail-closed target `unresolved:<path>`, which `decide()` routes to `REVIEW` (`UNRESOLVED_FILE_TARGET`). The earlier collector dropped all relative opens, so `process.chdir("$HOME/.aws")` followed by `readFileSync("credentials")` produced no observation at all and audited `ALLOW`; `fixtures/credential-attempt-relative` is the standing regression.
- **Collector output is parsed only from a root-owned trace on a volume the tool cannot reach, extracted by a trusted helper.** The trace is written by root-run `strace` into `/obs`, a named Docker volume (`safe402-obs-<auditId>-<attempt>`) seeded from the image's own `/obs` directory, created `mode 0700` root:root at image build time (`RUN mkdir -m 0700 /obs`, `runner/images/Dockerfile`) — a mode the traced (unprivileged) tool process cannot read, write, or unlink. The tool container has no writable host mount for observation data at all. After the tool container exits (or is force-killed on a deadline — `dockerKill` runs unconditionally before extraction, on every path including a throw), a separate **trusted helper container** — another instance of the same runner image, never the tool's own process — mounts the volume read-only and a host directory read-write, and copies the trace out (`dockerExtractTrace`, `runner/harness/docker.ts`); the volume is then deleted in the same `finally` block with `dockerVolumeRmRetry`, which retries briefly because a `--rm` teardown can still hold it open. The same `finally` runs on every path — normal exit, grace kill, deadline kill, or a throw. Symmetrically, a volume of that name leaked by an earlier crash is purged (`dockerVolumeRm`) **before** the tool container starts, so a previous run's trace can never be parsed as this run's evidence; container and volume names both carry the attempt number (`safe402-<auditId>-<attempt>`, `safe402-obs-<auditId>-<attempt>`) so a retry cannot inherit the prior attempt's volume either. The host-side reader additionally requires the copied path to be a genuine regular file (`lstatSync(...).isFile()`, so a symlinked forgery reads as missing) no larger than 64 MiB, failing closed with `collectorError: 'trace log too large'` otherwise (`runner/harness/run.ts`). `parseStrace` reads only that verified host-side file; the tool process never has a path to influence what the collector records. Integration test `runner integration > delivers the genuine trace from a killed container that tried to forge one` (`test/integration/runner.test.ts`) exercises a fixture that never exits and, while running, tries to truncate, overwrite, and unlink the live trace (all `EACCES`) and tries to write a forged trace to the old `/out` path, which no longer exists in the tool container (`ENOENT`); the extracted host trace contains none of the tool's tamper attempts.
- **ed25519 signature over the report hash.** `signReport` recomputes `hashCanonical('safe402/report/v1', report)` and refuses to sign unless it matches the caller-supplied `reportHash`, then signs that hash with the issuer's ed25519 key. `verifyEnvelope` (`src/reports/verify.ts`) independently recomputes the report hash, checks the issuer is in the trusted-issuer set, and verifies the signature over that hash — never over the raw report body — so a tampered report body fails at the `reportHash` check before signature verification is even reached. Covered by `test/reports.test.ts` ("round-trips a signed envelope", "rejects a tampered report body at reportHash", "rejects a flipped signature").
- **Capsule hash binding.** The signed report embeds both the decision capsule and a `capsuleHash` computed under the `safe402/capsule/v1` domain tag; `verifyEnvelope` recomputes that hash from the embedded capsule and rejects the envelope if it does not match, so the capsule inside a verified report cannot be swapped for a different one after signing. Covered by `test/reports.test.ts` ("rejects a re-signed report whose `capsuleHash` does not bind its capsule").

A verified envelope (`verifyEnvelope(...).ok === true`) means: the body hashes to the claimed `reportHash`, a trusted issuer signed that hash, the embedded capsule hashes to the claimed `capsuleHash`, and the capsule has not expired. It does **not** by itself mean the artifact, policy, subject, or execution profile match what the caller intends to run — a caller must separately check `capsule.artifactHash`, `capsule.policyCommitment`, `capsule.subjectId`, and `capsule.executionProfileHash` against its own expectations, and check revocation. `src/reports/verify.ts` documents this obligation directly above `VerifyResult`.

## What is not claimed

- **No enclave attestation in `LOCAL` mode.** Nothing in this phase runs inside a TEE, and no attestation quote of any kind is produced or checked. A verified signature proves the report was signed by a key the verifier trusts; it does not prove anything about the environment that computed the decision. Do not describe a hash comparison, a signature check, or Docker isolation as "attestation."
- **Environment-variable reads are not observable after process start.** The strace collector traces `openat`, `open`, `connect`, `sendto`, `execve`, `chdir`, `fchdir`, `clone`/`clone3`, `fork`, and `vfork`. A tool that reads `process.env` inside its own address space performs no syscall the collector traces, so credential material placed in an environment variable and read (not exec'd or written to a canary path) leaves no observation. Safe402 never places real secrets in the tool's environment for this reason, but this is a real observational gap, not just a hygiene practice — a tool that reads and exfiltrates an env var over a *declared* connection would show `ALL_CHECKS_SATISFIED`.
- **No hostname recovery for failed DNS lookups.** `parseStrace` records failed `connect` attempts, but a failed DNS resolution never reaches `connect` with a resolved address, so the hostname a tool tried to look up is not recovered from the trace when resolution itself fails.
- **A deadline kill can still yield an incomplete or missing trace.** When a tool exceeds `profile.deadlineMs`, the host force-kills the tool container (`docker kill`) before the trusted helper container extracts whatever is in the named volume. Because the volume's lifecycle is independent of the tool container, whatever `strace` had already flushed to the trace file at the moment of the kill can usually still be recovered — an improvement over an earlier design where the copy step ran only in the tool container's own exit path and a kill lost the trace outright. But recovery is still not guaranteed: anything `strace` had not yet flushed is gone, and the extraction can just as well find nothing. `decide()` treats every outcome the same way regardless — `coverage.timedOut` and a missing, empty, or oversized trace all route to `REVIEW`, never `ALLOW`. Integration test `runner integration > kills on deadline` (`test/integration/runner.test.ts`) accepts either a genuine partial trace (`collectorError === null`) or `'trace log missing'`, and asserts the recovered trace never contains tool-authored bytes either way. Flagged **REVIEW** in the sense that Safe402 never claims a timed-out run was clean, but the evidence for *why* it timed out may be partial or absent.
- **An unresolvable file target names no file.** When the collector cannot place an open — an `openat` against a directory fd it never saw opened, or a relative path in a process whose cwd it lost — the observation carries `unresolved:<path>` and the audit becomes `REVIEW`, never `ALLOW`. That is deliberately *not* a `BLOCK`: the engine cannot say which file was touched, so it cannot say the access was undeclared either. A report carrying `UNRESOLVED_FILE_TARGET` means "some file access is unaccounted for", nothing more precise.
- **A completed connection to a bare IP address is not flagged as undeclared.** `decide()`'s network check (`hostOf` in `src/domain/decide.ts`) treats a target that is a literal IP address (or has no resolvable hostname) as unattributable rather than undeclared, because without DNS-to-connect correlation, blocking every bare-IP connect would also block a tool legitimately connecting to its own declared host's resolved address. This is unreachable today because `ExecutionProfile.network` is `none` for every profile in this phase (no completed network connections are possible at all), but it is a real gap that Phase 4's network-enabled profiles and collector DNS correlation must close — it is not silently safe by design, only currently unreachable.
- **Docker is not proof of safe arbitrary-code execution.** The runner's isolation reduces the blast radius of a submitted tool (no network, read-only root filesystem, dropped capabilities, resource limits, a host-enforced deadline) but is not a sandbox guarantee against a container-escape or kernel exploit. Safe402 restricts audited artifacts to repository-controlled fixtures in this phase specifically because general, untrusted code execution has not been proven safe by anything in this pipeline.
- **CRE (Phase 4) protects secret policy *parameters*, not policy *logic*.** When Chainlink CRE confidential workflows are integrated in a later phase, the TEE-backed `handlerInTee` path protects values delivered through the CRE secrets mechanism (for example a private threshold parameter) from node operators. It does not hide or attest to the workflow's decision logic itself — the compiled WASM is visible, and Safe402 must never describe CRE confidentiality as protecting or attesting to policy logic.
